Executive Summary

Most of the problems are pre-launch noise: divisions that exist before they have real work, while the divisions that are ACTIVE are doing heavy, overlapping work without clear boundaries.

Problems

Current Structural Problems

Five root-cause issues driving most of the fragmentation.

  1. ⚠
    Over-divisioning for pre-launch scale. 23 divisions for a product that isn't launched. Many divisions have 1 file and negligible workload. The organizational overhead exceeds the organizational value. A pre-launch AI EdTech startup needs maybe 10 active divisions, not 23.
  2. ⚠
    Same function split into multiple divisions. Finance/FinOps, Business/Marketing, Sales/Partnership, DevOps/Operations/Production Admin, QA/Code Review. Each split adds a handoff that creates friction, ambiguity, and boundary confusion. At AI-team scale, these handoffs slow everything down.
  3. ⇿
    Lifecycle status inconsistency. Divisions have four statuses (ACTIVE, PREPARED, STANDBY) defined differently per division. "ACTIVE" means "requires work now" for Legal/Finance/Management but "will need work post-launch" for Security/Production Admin. The status system is not actionable — it doesn't tell you what to do RIGHT NOW.
  4. ⇿
    Engineering cluster has too many quality layers. Development, QA, Code Review, Security, DevOps, Production Admin, Architecture — 7 divisions touching the same codebase with overlapping responsibilities. Development does the work; the other 6 add latency. Three quality gates (QA → Code Review → Security) before a feature ships creates a bottleneck that doesn't exist at this team size.
  5. ⇿
    Academic Content is not a division. One file (knowledge-base.md) describing domain knowledge for the AI team is not a division. It reads as a placeholder created to fill the organizational chart, not to serve a real function.

Governance

Management Principle for Future Org Decisions

A decision framework for evaluating future division changes.

The 5-Person Rule

At the scale of an AI EdTech startup with a small team, every division needs to justify its existence with work, not theory. Before creating a new division, ask:

  1. Who does the work? Can existing divisions absorb it, or does this need a dedicated owner?
  2. Does it overlap? Is another division already doing this or adjacent to it?
  3. What's the lifecycle? ACTIVE now, or PREPARED for later? Don't create divisions before the work exists.
  4. Is it a knowledge asset or a division? A README with domain knowledge is not a division. A team that produces regular output is.
  5. What's the handoff cost? If two divisions depend on each other for every decision, they should be one division.

Lifecycle Status Definition (Standardize This)

Standardize lifecycle definitions across all divisions so status is actionable:

StatusDefinitionAction
ACTIVEWork exists NOW. Needs regular attention.Resource immediately
PREPAREDStrategy done, waiting on prerequisite (product stability, data volume, team size).Maintain docs, monitor trigger condition
STANDBYNo work exists yet. Activates on specific future event (first user, first human hire, first institutional deal).Keep template only
DORMANTWork was done, now paused. Not the same as STANDBY.Archive, don't maintain

Division Creation Protocol

Before creating a new division, the Management division must confirm:

  1. The work is not absorbable by an existing division
  2. The work requires a dedicated owner (not shared responsibility)
  3. The trigger condition for activation is measurable (not "someday")
  4. The division's boundaries are defined and don't overlap with adjacent divisions
  5. Documentation exists in the new division's folder before it is ACTIVE
