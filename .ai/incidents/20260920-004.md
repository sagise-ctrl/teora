# Incident Report: Analyze Pipeline Empty Workspace (DB Constraint + UX + Observability)

## Metadata
- **ID:** 20260920-004 (INC-011)
- **Detected:** 2026-09-20 (owner reported empty workspace on Academic project 25 after Begin Analyze)
- **Severity:** P1 High (Begin Analyze broken end-to-end + no UX feedback when pipeline fails)
- **Status:** RESOLVED (commit `f50e7a4`, backend deploy `dpl_6U7rXUDQJo9wwYE9jN5ihNrK8YMQ`, frontend deploy `dpl_CH9BpT5VPKnWjyqbYaqRCW2YmZmo`)

## Summary

Three bugs converged to make Begin Analyze silently produce an empty workspace:

1. **Bug 1 (DB layer):** AI prompt asked for free-form `taskType` ("makalah", "skripsi", "artikel") but `project_metadata.task_type` had a CHECK constraint inherited from `projects.task_type` that only allowed the enum `general|academic|dashboard_chat`. AI's natural-language output violated the constraint → entire transaction rolled back → no document + no outline + no job status update written.

2. **Bug 2 (UX layer):** Analyze + document generation routes use `waitUntil` and return 202 immediately. The client never sees the error. Owner just saw an empty workspace with no toast, no alert, nothing to indicate failure.

3. **Bug 3 (observability):** `jobs.errorMessage` was truncated at 500 chars, hiding Postgres CHECK constraint errors that start with the most informative text. The truncated string in the jobs table was useless for debugging.

Surfaced only after INC-009 (waitUntil fix) and INC-010 (Olagon model alias) were both applied — without them, the pipeline was timing out or returning a model error before this layer could be reached.

## Affected Features

- **Endpoint:** `POST /api/projects/:projectId/analyze` — pipeline (2 sequential AI calls + DB transaction). Failed at the transaction step (Step 5b: project_metadata upsert).
- **Endpoint:** `POST /api/projects/:projectId/documents/generate` — same failure mode for the write_chapter job.

## User Impact

- **Direct user impact:** Owner only (sole user at time of report)
- **Frequency:** 100% — every Begin Analyze attempt with non-trivial `instructionText` would have either produced empty workspace OR never succeeded
- **Wasted time:** ~15 min owner debugging between INC-009/INC-010 deployments and this fix

## Root Cause (CONFIRMED)

### Bug 1: AI free-form vs DB enum constraint

**Layer:** Backend AI integration + DB schema (`routes/projects.ts:429`, `project_metadata` table)

```typescript
// routes/projects.ts:429 (BEFORE)
{
  "detectedTitle": "...",
  "taskType": "jenis tugas (makalah/skripsi/laporan/esai/dll)",  // ← free-form
  ...
}
```

```sql
-- DB constraint (inherited from projects table)
CHECK (((task_type IS NULL) OR (task_type = ANY (ARRAY['general', 'academic', 'dashboard_chat']))))
```

**Direct verification:**
```sql
UPDATE project_metadata SET task_type = 'artikel' WHERE id = ...;
-- ERROR: 23514 (check_violation): new row for relation "project_metadata" violates check constraint "project_metadata_task_type_check"

SELECT task_type, COUNT(*) FROM project_metadata GROUP BY task_type;
-- All 6 rows: NULL (proves every previous attempt rolled back at the metadata insert)
```

**Why older projects (1-8) appeared to work:** AI didn't always return `taskType` in the JSON, and NULL bypasses the CHECK constraint. Most projects with NULL `task_type` worked. Newer AI models are more compliant with the prompt format → always include `taskType` → always fail.

### Bug 2: Silent async pipeline failure

**Layer:** Frontend UX (`pages/project.tsx`)

The analyze + document routes use `waitUntil` to keep the function alive after returning 202. Errors are caught and logged to the jobs table, but the frontend has no polling listener for `status === "failed"` jobs. Owner sees:
- "Analysis started" toast (from `analyzeProject.mutate({...}, { onSuccess: ... })`)
- Empty workspace

No subsequent feedback ever arrives. Same applies to "Begin Analyzer" button → `analyzeProject.mutate` → 202 → empty workspace → confused user.

### Bug 3: Error message truncated at 500 chars

**Layer:** Backend error persistence (`routes/projects.ts:397`, `routes/projects.ts:895`)

```typescript
// BEFORE
errorMessage: message.slice(0, 500),
```

Postgres CHECK constraint errors are ~800 chars in Drizzle/Postgres error format. Truncating at 500 chars cut them off mid-stack — the most useful debugging info (the constraint name + offending value) was at the beginning, but the full error class (`DrizzleQueryError`) and the SQL state (`23514`) was lost.

## Resolution

### Fix layers (commit `f50e7a4`)

**1. DB schema split (Owner chose Option C):**
```sql
ALTER TABLE project_metadata RENAME COLUMN task_type TO task_subtype;
ALTER TABLE project_metadata ADD COLUMN task_category text;
ALTER TABLE project_metadata ADD CONSTRAINT project_metadata_task_category_check
  CHECK (task_category IS NULL OR task_category IN ('general', 'academic', 'dashboard_chat'));
ALTER TABLE project_metadata DROP CONSTRAINT project_metadata_task_type_check; -- inherited
```

`task_subtype` is now free-form (accepts "artikel", "makalah", "skripsi", etc.). `task_category` carries the enum semantic.

**2. Drizzle schema (`lib/db/src/schema/project_metadata.ts`):**
- `taskType` → split into `taskCategory` + `taskSubtype` columns
- Drizzle CHECK constraint NOT declared in table expression (would conflict with existing DB constraint; matches INC-008 pattern for raw-SQL CHECK constraints)

**3. AI prompt (`routes/projects.ts:429`):**
```typescript
{
  ...
  "taskCategory": "kategori tugas — HARUS salah satu dari: 'general' (tugas pendek/sederhana), 'academic' (karya ilmiah multi-bab), 'dashboard_chat' (internal scratchpad). WAJIB pilih satu.",
  "taskSubtype": "subtipe tugas dalam bahasa natural — contoh: 'makalah', 'skripsi', 'artikel jurnal', 'laporan', 'esai', 'review', 'thesis', 'dissertation', 'paper', 'studi kasus'. Bebas string apa pun.",
  ...
}
```

Prompt now explicitly tells the AI to use the enum for `taskCategory` and free-form for `taskSubtype`. The two are independent.

**4. Transaction (`routes/projects.ts:484-518`):**
- `project_metadata` upsert writes both fields
- `projects.task_type` mirrors `task_category` (still enum-constrained for routing/theme compatibility)

**5. Frontend UX (`pages/project.tsx`):**
```typescript
const notifiedFailedJobsRef = useRef<Set<number>>(new Set())
useEffect(() => {
  if (!jobs) return
  for (const job of jobs) {
    if (job.status === "failed" && !notifiedFailedJobsRef.current.has(job.id)) {
      notifiedFailedJobsRef.current.add(job.id)
      const jobLabel = job.jobType === "analyze" ? "Analyze" : "Document generation"
      const desc = (job.errorMessage ?? "").slice(0, 240) || "Pipeline gagal. Coba lagi."
      toast({
        title: `${jobLabel} gagal`,
        description: desc,
        variant: "destructive",
        duration: 8000,
      })
    }
  }
}, [jobs, toast])

// Reset tracker on project change
useEffect(() => {
  notifiedFailedJobsRef.current = new Set()
}, [projectId])
```

**6. Observability (`routes/projects.ts:397`, `routes/projects.ts:895`):**
- `message.slice(0, 500)` → `message.slice(0, 4000)`
- Full error already logged via `logger.error({ err, projectId, jobId }, "...")` (Vercel runtime logs capture stack)

**7. OpenAPI + codegen:**
- `ProjectMetadata` schema updated to expose `taskCategory` + `taskSubtype` instead of `taskType`
- Orval regenerated Zod + React Query types

## Pattern Classes (NEW)

- **`ai_freeform_output_db_enum_constraint_mismatch`** (1x — promote after 2x). Covers: any AI prompt that asks for a value going to a CHECK-constrained column — prompt must restrict output to enum, free-form goes to a separate column. Sibling: `db_constraint_gap_openapi_db_mismatch` (INC-008 pattern).
- **`waituntil_pipeline_silent_failure`** (1x — promote after 2x). Covers: any backend pipeline that uses `waitUntil` without a frontend watcher on job status — failures become silent.
- **`error_message_truncation_hides_db_constraint_errors`** (1x — promote after 2x). Covers: any error message field that's sliced to <800 chars truncates Postgres CHECK violation info.
